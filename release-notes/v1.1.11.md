# WAVE v1.1.11

**Release date:** 2026-05-07

## What's in this release

v1.1.11 is the first **dual-architecture** release with working auto-update on both 64-bit and 32-bit Windows. It carries forward all the fixes that landed in v1.1.10, plus a correction to the release workflow itself.

If you're updating from v1.1.10, this is purely a packaging/CI fix — there are no user-visible feature changes.
If you're updating from v1.1.6 – v1.1.9, see the **One-time manual install** note below.

## Bug fixes (carried over from v1.1.10)

### x64 PCs were getting the 32-bit build via auto-update

**Fixed:** the auto-updater could deliver the 32-bit (ia32) package to a 64-bit Windows machine, leaving the app unable to launch.

The release workflow used to pack both architectures with Velopack's default channel, so each pack produced a `releases.win.json` feed file. The upload step then overwrote the x64 feed with the ia32 feed, and every client — regardless of architecture — pulled the 32-bit nupkg.

The workflow now pins each architecture to its own Velopack channel:

- 64-bit builds use channel `win-x64` → feed file `releases.win-x64.json`
- 32-bit builds use channel `win-x86` → feed file `releases.win-x86.json`

Each installer is permanently bound to its channel at pack time, so 64-bit installs can only ever see 64-bit updates, and vice versa.

### 32-bit builds crashed on launch with "no precompiled module found"

**Fixed:** Velopack's native loader (`velopack/lib/load.js`) registers the 32-bit Windows native under the key `"win32-x86-msvc"`, but the `@neon-rs/load` dispatcher reports the running platform as `"win32-ia32-msvc"`. The mismatch caused every 32-bit launch to crash with:

```
Error: no precompiled module found for win32-ia32-msvc
```

A `postinstall` script (`scripts/patch-velopack.cjs`) now patches `node_modules/velopack/lib/load.js` to add `"win32-ia32-msvc"` as an alias for the existing 32-bit native module. The patch is idempotent and runs automatically on every `pnpm install`.

## New in v1.1.11

### Release workflow no longer fails on the second arch upload

The v1.1.10 workflow tried to call `vpk upload github --publish` once per architecture. The second call failed with:

```
There is already an existing release tagged 'v1.1.10'.
Please delete this release or provide a new version number.
```

…because `vpk upload --publish` insists on creating a fresh release and refuses to attach assets to an existing one. As a result, **v1.1.10 was published with x64 assets only — no 32-bit installer**.

The workflow now uses `vpk upload github` for the x64 channel (which creates the release and attaches x64 assets) and `gh release upload` for the ia32 channel (which simply attaches the x86 assets to the same release). Channel-suffixed filenames (`releases.win-x64.json` vs `releases.win-x86.json`) ensure the two channels never collide.

## One-time manual install required from v1.1.6 – v1.1.10

Anyone currently running **v1.1.6 through v1.1.10** — including 64-bit machines that were incorrectly upgraded to the 32-bit build — must **download and install the correct package manually one time** from the GitHub Releases page:

- 64-bit Windows → `com.ntamadakis.wave-win-Setup.exe`
- 32-bit Windows → `com.ntamadakis.wave-x86-win-Setup.exe`

From v1.1.11 onward, the in-app updater stays on the right architecture automatically.

> **Note for existing v1.1.10 users:** the v1.1.10 release on GitHub only contains the 64-bit assets, so 32-bit users could not install v1.1.10 at all. v1.1.11 is the first version where the 32-bit installer is actually published.

## Changes

- Version bumped from `1.1.10` → `1.1.11`
- `.github/workflows/release.yml`: replaced the second `vpk upload github --publish` call with `gh release upload --clobber` so the ia32 channel attaches to the existing release without trying to create a new one
- All v1.1.10 fixes (channel separation, ia32 loader patch, postinstall script) carry forward unchanged

## How to release future versions

1. Bump `version` in `package.json`
2. Add release notes file `release-notes/vX.Y.Z.md`
3. Create and push a tag: `git tag vX.Y.Z && git push origin vX.Y.Z`
4. GitHub Actions builds the app, packs it with `vpk` (per-channel), and uploads to GitHub Releases automatically
5. Users on v1.1.11+ will receive the update silently on next launch — staying within their architecture
